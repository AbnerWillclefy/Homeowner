# The Go backend

Related: [ADR 0004](../adr/0004-ai-allocates-behind-a-deterministic-referee.md), [ADR 0002](../adr/0002-mirror-the-work-stack.md). Terms: **Allocation**, **Day Plan** in [CONTEXT.md](../../CONTEXT.md).

The backend is one Go module in `backend/`. In Go, code under `internal/` can only be imported from inside this module, and each folder is a *package*. `cmd/<name>/` holds a program's `main` function, an *entry point*.

## Entry points

| Entry point | Status | What it does |
|---|---|---|
| `cmd/api` | Built | `api` or `api serve` runs the HTTP server; `api migrate` applies database migrations and exits; `api vapid` prints a new VAPID key pair (a one-off human step, needs no database). |
| `api allocate` | Built | Runs the Allocation job once and exits: plans every Home whose Allocation time has arrived, then sends the push nudges when VAPID keys are set (for local runs and manual catch-up). |
| `cmd/evals` | Built | `go run ./cmd/evals` runs the manual allocator evals (baseline against the LLM allocator on synthetic days) and prints a comparison table; a separate binary, never in the API image and never run by `go test` or CI. See "Evals" in [Daily Allocation](allocation.md). |
| `api events` | Built | The Allocation job's Lambda: serves only `POST /events` (the scheduled tick that Lambda Web Adapter forwards) and `GET /healthz`. Same image as the API, a different command; see [ADR 0008](../adr/0008-scheduled-jobs-run-as-a-second-lambda-from-the-api-image.md). |

## Packages

The code is organised by domain ([ADR 0011](../adr/0011-split-each-domain-into-layer-folders.md)). Each domain package owns its data, its rules and its HTTP routes, and names its files by layer, so the same file name means the same job everywhere:

| File | Layer |
|---|---|
| `<package>.go` | The package doc, the domain model types and the sentinel errors (when the package has more than one file). |
| `handler.go` (`handler_<topic>.go` when one is not enough) | The HTTP controller: a `Handler` built with `NewHandler`, one method per route, which decodes the request, calls the domain and maps its errors to status codes. |
| `dto.go` | The named request and response shapes on the wire. Small inline body structs stay in the handler. |
| `store.go` | The repository: the only file that talks to Postgres. |
| any other file | The service: the domain's rules, for example `validate.go`, `resolve.go`, `schedule.go`, `commit.go`. |
| `handler_test.go` | The black-box API tests of that domain's routes, through the real server (`apitest`). |

Folders:

- `internal/<domain>/`: `users`, `homes`, `invites`, `chores`, `choresettings`, `catalog`, `profile`, `tasks`, `dayplan`, `checkin`, `streak`, `push`, `photos`, plus the pure rule packages `allocation`, `schedule`, `onboarding` and the shared ids in `vocab`.
- `internal/identity/`: who is calling. The server's middleware puts the signed-in User and their Membership in the request context; handlers read them with `identity.CurrentUser` and `identity.CurrentMembership`, so no domain imports another just to know its caller. `users.User`, `homes.Home` and `homes.Membership` are aliases of its types.
- `internal/platform/`: code that knows no domain. `auth` (token verification), `clock`, `config`, `db`, `httpx` (`WriteJSON`, `WriteError`, `InternalError`, `DecodeBody`), the test harness `apitest` and `puritytest`, the shared check behind every `purity_test.go`.
- `internal/server/`: the composition root. `server.go` builds every domain `Handler` and lists every route in one table; `auth.go` holds `requireUser` and `requireResident`; `cors.go` and `http.go` the outer middleware.

Every domain handler also imports `identity`, `platform/httpx` and, where it needs the time, `platform/clock`; those arrows are left out. `allocation` imports nothing from the project and does no I/O (`purity_test.go` enforces that). `schedule` and `tasks` import it only for its `Date` type; `dayplan` is the only package that calls `Plan` and `Check`. The purity tests of `allocation`, `schedule` and `onboarding` cover the whole package; `catalog` exempts its `handler.go` and `checkin` its `store.go`, so the rule files stay pure next to their edge.

| Package | Role |
|---|---|
| `server` | Builds one `http.Handler` (`server.New(Deps)`): it constructs each domain's `Handler` and maps every route to one of their methods behind `requireUser` or `requireResident`. `Deps` holds everything outside the system that tests fake: database pool, clock, logger, CORS origins, the Web Push `Sender` and the public VAPID key, the token `Verifier` (nil means auth is off), and the photo `ObjectStore` with `PhotosBaseURL` (nil means photos are off). |
| `platform/config` | Reads `DATABASE_URL`, `MIGRATE_DATABASE_URL`, `PORT`, `MIGRATE_ON_START`, `DB_MAX_CONNS`, `CORS_ALLOWED_ORIGINS`, the optional pair `COGNITO_ISSUER` and `COGNITO_CLIENT_ID` (public identifiers, so plain environment variables; one without the other is an error, the issuer must be https, neither means auth is off), and the optional set `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (one key without the other is an error; neither means push is off). `VAPID_PRIVATE_KEY` is resolved from SSM through `VAPID_PRIVATE_KEY_SSM_PARAM`, like the database URLs. The LLM allocator settings: `LLM_ALLOCATOR_ENABLED` (default false; true needs `ANTHROPIC_API_KEY`, resolved from SSM through `ANTHROPIC_API_KEY_SSM_PARAM`), `LLM_MODEL` (default `claude-haiku-5-5`), `LLM_DAILY_CAP_PER_HOME` (default 3) and `LLM_TIMEOUT_SECONDS` (default 15); errors name the variable, never the key. The optional pair `PHOTOS_BUCKET` and `PHOTOS_BASE_URL` (one without the other is a startup error; the base URL must be https and is stored without a trailing slash; neither means the photo routes answer 503; `PhotosEnabled()`). `REPLAN_ALLOCATE_FUNCTION_NAME` (trimmed; empty or unset means off, the default) is the name of the Allocation function that `POST /dev/replan` invokes; only the staging API sets it. |
| `photos` | A User's photo. `ObjectStore` is the private-bucket seam (`PresignPut`, `Head`, `ReadPrefix`, `Copy`, `Delete`), nil in `server.Deps.Photos` when photos are off. `S3` is the real adapter over `aws-sdk-go-v2/service/s3`: `PresignPut` signs a PUT with `ContentType` and `ContentLength` set (both signed headers, so the upload binds the type and exact size) for 5 minutes with the API role's own credentials, so that role needs `s3:PutObject`; `Head` returns size, type and ETag and maps only S3's 404 to `ErrNotFound` (the API role holds `s3:ListBucket`, so a missing key answers 404); any other error, a 403 included, is wrapped and the handler answers 500; `ReadPrefix` is a ranged GET of 16 bytes; `Copy` is `CopyObject` with `MetadataDirective: REPLACE`, the content type, `Cache-Control: public, max-age=86400, immutable` and `CopySourceIfMatch` set to the ETag `Head` returned, so an object replaced after the checks answers 412, which is `ErrChanged` and a `400 invalid_object` from Confirm. `Fake` is the in-memory store for tests (`Upload` simulates the browser's PUT, `Objects`, `Presigned`, `FailDelete`). `keys.go` holds the pure rules: `NewPendingKey(userID)` is `pending/<userID>/<22 chars of 128 random bits>`, `NewAvatarKey(ext)` is `avatars/<fresh id>.<webp or jpg>` (a fresh id, so a pending key and a public URL never link), `OwnsPendingKey` is a strict regex that includes the caller's id (how a User can only confirm a key issued to them, with no table), `Sniff` reads the magic bytes (JPEG `FF D8 FF`; WebP `RIFF` at 0-3 and `WEBP` at 8-11) and `URLBuilder` turns a stored key into `PHOTOS_BASE_URL/<id>.<ext>`, returning nil for a nil key or an empty base (`server.New` passes an empty base when `Deps.Photos` is nil). `Handler` serves the three routes behind `RequireConfigured` (`503 {"error":"photos not configured"}`). Confirm checks, in order, key ownership (`invalid_key`), existence (`not_found`), size and type (`invalid_object`) and magic bytes against the stored type (`not_an_image`), each a `400` that changes nothing; then copies to the avatar key, stores it and, only after that commit, deletes the pending object and the previous photo, best effort (a failure is logged at warn with the key and never fails the request). Magic bytes prove the type, not that the image decodes. |
| `push` | `Sender` interface (one `Send` per subscription, returning `ErrGone` when the push service answers 404 or 410), `WebPushSender` (real, on `webpush-go`, VAPID, 24h TTL, 10s HTTP timeout; it strips a leading `mailto:` from `VAPID_SUBJECT` because webpush-go adds one, and includes the push service's response body in non-2xx errors), `Payload` (`title`, `body`, `url` and an optional `kind`, `checkin_reminder` or `day_plan_ready`, that the service worker words for the device language; the English text is always sent too), `Store` (the `push_subscriptions` table: upsert, get, `ListByUsers` (all devices of a set of Users in one query), delete, and `Deliver`, which drops a subscription the push service rejected), and `Fake` for tests. |
| `platform/auth` | `Verifier` interface: a raw bearer token in, `Claims{Subject, Email}` out, or an error wrapping `ErrInvalidToken`. `Cognito` is the real one: RS256 only, signature from the pool's JWKS (fetched lazily on the first authenticated request, cached in memory for an hour, one refetch at most a minute for an unknown key id, old keys kept if a refresh fails, fail closed when none are known), `iss` equal to the issuer, `aud` equal to the app client, `token_use` equal to `id`, `exp` required, `email_verified` true, subject and email present. Time comes from the injected `Clock`. `Fake` mints tokens for tests and never touches the network. |
| `users` | `Store.FindOrCreate(sub, email, now)`: the single upsert behind the first-request-creates-the-User rule; it also returns `display_name` and `photo_key`, so every request's `identity.User` carries them. `Store.SetDisplayName` is one `UPDATE` that stores `NULLIF(name, '')`, so "" clears. `name.go` holds the pure rule `NormalizeName` (trim, "" when blank, 40 code points, no control or bidi characters), which answers `ErrNameTooLong` or `ErrNameInvalid`; `identity.ShownName` (display name, else the email before the last `@`) is shared with `homes`. `dto.go` holds `MeResponse`, whose `photoUrl` comes from the photo URL builder `Handler` is given. `Store.SetPhotoKey` and `ClearPhotoKey` are each one `UPDATE ... FROM (SELECT ... FOR UPDATE)` that returns the previous key, so two simultaneous confirms each get the right key to delete; `photos` uses them through its `Keys` interface (`users` never imports `photos`). |
| `onboarding` | The ordered step ids (`install`, `reminders`, `baseline`, `restrictions`, `preferences`, `home`, then `done`), `Valid` (what a client may `PUT`), `Next` (the step after the stored one) and `Before` (the stored values a step may move forward from). Stdlib only; `purity_test.go` enforces it. `users.Store.AdvanceOnboarding` applies the monotonic rule as one conditional `UPDATE`, and `homes.Store.Create` stores `done` in its transaction. |
| `homes` | `Membership{ResidentID, Home}` is a User's place in a Home: their own `residents` row and the plain `Home`. `Store.Create(userID, timezone, allocationTime, now, inHome)` inserts the Home and the first Resident in one transaction (and runs the optional `inHome` callback on it, which `POST /home` uses to add the reviewed Chores without `homes` importing `chores`) and maps the unique violation on `residents.user_id` to `ErrAlreadyResident`; `ForUser` returns the caller's `Membership` or `ErrNoHome`; `UpdateSettings` replaces the timezone and Allocation time. `LeaveTx(tx, residentID, homeID)` is the one place a Resident leaves a Home: inside the caller's transaction it locks the Home row (`FOR UPDATE`, so two last Residents leaving at once are serialised), deletes the `residents` row (the cascade clears their specific Preferences and Restrictions) and deletes the Home if nobody is left (the cascade clears its Chores, Tasks and Invites). Accepting an Invite uses it, and `Store.Leave(residentID, homeID)` wraps it in its own transaction for `DELETE /home/residents/me`. |
| `invites` | An Invite is a single-use link, valid while `now < expires_at` (`Validity`, seven days; at the exact instant it is expired). The token is 32 random bytes, base64url, shown once; only its SHA-256 is stored, and a token that is not canonical base64url of 32 bytes is `ErrNotFound` before the database is asked. `check` (pure) is the validity rule and `newToken`/`hashToken` are pure too. `Store.Create` caps a Home at `MaxOpenPerHome` (10) unused, unexpired Invites (`ErrTooManyOpen`), serialised by a `FOR NO KEY UPDATE` lock on the Home row. `Lookup` never writes. `Accept` is one transaction: claim the Invite with `UPDATE ... WHERE used_at IS NULL AND expires_at > now RETURNING home_id` (the single-use guard; on zero rows a read decides `ErrNotFound`, `ErrUsed` or `ErrExpired`), then if the User lives in the same Home `ErrAlreadyHere`, in another Home without `confirmLeave` `ErrWouldLeaveHome`, with it `homes.LeaveTx`, then insert the `residents` row (a unique violation is `homes.ErrAlreadyResident`). Any error rolls the claim back, so a failed join never burns the Invite. Imports `homes`, never the reverse. No HTTP types. |
| `profile` | `Store` for the User's profile: `Load`, `SetBaseline` (set some days, clear others, one transaction), `SetPreference` (neutral deletes the row), `AddRestriction`, `RemoveRestriction`. Writes are idempotent. `MaxBaseline` (20) is the named upper bound of a Baseline. |
| `chores` | `Validate(Input)` is pure: it trims the name, de-duplicates and sorts Demands and weekdays, and returns a stable code per invalid field, all at once (`Input` is decoded straight from the JSON body; numbers arrive as `any`, so a string or 2.5 is a field code, not a bad request; the first code recorded for a field wins). `Store` has `List`, `Create`, `Update`, `Delete`; every query that takes an id also filters on `home_id`, and a miss is `ErrNotFound`, and the handlers answer 404 for an id that fails `ValidID` without asking the Store. Imports `vocab` for Categories, Demands and Importances. `Chore` carries the JSON tags and is written to the response as is. |
| `catalog` | The fixed Catalog of common Chores and the rules that turn questionnaire answers into proposed Chores; Go code, no table, no migration. Pure (stdlib and `chores.Fields` only; `purity_test.go` enforces it). `Entries()` returns copies of the Catalog table in display order; each entry carries its own rule (how many Chores the answers call for, and an optional adjustment of Effort, interval or weekdays), so adding an entry is one place. An entry has a stable `ID` (for example `clean_bathroom`), `chores.Fields` with an English fallback name, and `PerRoom`. `Answers` is decoded like `chores.Input` (counts and weekdays as `any`); `ValidateAnswers` returns codes (`invalid`, `out_of_range`, `unknown`) keyed `rooms.bathrooms`, `collection.trash`, `habits.cooking`, all at once; a missing section means none (cooking defaults to `sometimes`). `Propose(Answers)` is deterministic and follows Catalog order: a per-room entry yields one `Proposal` per room (`Instance` 1-based, `nil` when there is one), pets add `pets` Chores, a collection stream with days adds one weekly essential Chore limited to those weekdays, and habits change the Chores (a dishwasher swaps washing the dishes for loading it, no washing machine drops the laundry Chores, cooking `daily` makes the kitchen Chore heavier and more frequent). Bounds: 0 to 10 rooms per type (kitchens 0 to 3) and `MaxProposals` 80, which a test proves the largest answers stay under. The API never renders a localised name; the PWA names a Chore from `catalogId` and `instance`. |
| `choresettings` | A Resident's Preference and Restriction on one specific Chore. `Resolve(Chore, General, Specific)` is pure and holds the rule: a specific Preference (neutral included) beats the general one for the Chore's Category, else neutral (source `specific`, `general` or `default`); Restrictions only add, so the reasons are the Chore's Demands that are in the User's general Restrictions plus the specific Restriction, listed apart. `Store` has `SetPreference`, `ClearPreference`, `AddRestriction`, `RemoveRestriction` (idempotent; the two sets prove in the same statement that the Chore is in the Resident's Home, the two deletes ask only when they removed nothing; `ErrNotFound` otherwise, the same for a missing Chore) and `Effective(homeID)`, which reads the Home's Chores, Residents, all their general profiles (`profile.LoadMany`, one `ANY($1)` query per profile table) and the specific rows in one read-only repeatable-read transaction, a fixed number of queries however many Residents there are. It has no HTTP types, so the Allocation job can reuse it; `allocation` is untouched. |
| `schedule` | `Decide(Chore, latest *Task, today)` is pure (stdlib and `allocation.Date` only; `purity_test.go` enforces it) and returns one decision: `Open` a Task with a window and Effort, `SetEffort` on the open Task, or `Nothing`. Rules (ADR 0001): a recurring Chore has windows of N consecutive days, the first starting on the day it was created in the Home's zone; `WindowStart` and `WindowEnd` are inclusive dates. With allowed weekdays, the window starts on the first allowed day on or after the scheduled start and N is rounded up to whole weeks, so a Task only opens on an allowed day. A one-off Chore gets one Task, ever (a day, or a week when weekdays are limited). A window is missed when today is past `WindowEnd` and the Task is still open; the same Task stays open and keeps its window. Missed windows are derived (`floor((today - WindowStart) / length)`), never counted, so repeated or skipped runs agree; a recurring build-up Chore's current Effort is `min(5, base + missed)`, other Chores stay at base (`buildsUp` is ignored on a one-off). After a Task is done, the next window of a recurring Chore starts N days after `closed_on` at base Effort (an assumption until a Completion ticket defines it). |
| `tasks` | `RefreshIn(ctx, tx, homeID, date, loc, now)` brings a Home's Tasks up to date inside the caller's transaction, for the date and zone the caller already worked out: it sets `statement_timeout` to 5s with `SET LOCAL`, locks each Chore row `FOR UPDATE`, loads its latest Task, applies `schedule.Decide` and writes, then puts back the value it read first with `set_config('statement_timeout', ..., true)`, so the rest of the caller's transaction keeps its own setting, the session's or a `SET LOCAL` of its own (`SET LOCAL` lasts until the transaction ends). The Chore row locks are held until the caller commits, so a concurrent `GET /home/tasks` waits for a Day Plan run, which is short. `Store.Refresh(homeID, now)` is the pool wrapper for callers outside a run (`GET /home/tasks`): it opens a transaction, converts `now` to a date in the Home's IANA zone (an unloadable zone is an error, never UTC), calls `RefreshIn` and commits. Idempotent and safe in parallel; the partial unique index on open Tasks is the final guard and the insert is `ON CONFLICT DO NOTHING`. `Store.ListOpen(homeID)` returns the open pool, never nil. `dayplan` calls `RefreshIn` from its one transaction opener before it builds `allocation.State`. |
| `checkin` | The Check-in rule, pure (`checkin.go`, stdlib only; `purity_test.go` enforces it for every file but `store.go`). `Level` (`drained`, `low`, `normal`, `energized`) with `Valid`, and `Scale(base, Level)`: 0, 50%, 100%, 130% of the Baseline in whole points, rounded down (integer arithmetic), 0 for a base of 0 or an unknown level. Table-tested for every level and every base 0 to `profile.MaxBaseline`. Demand validation stays in `vocab.IsDemand`. |
| `checkin` (store) | `store.go` stores Check-ins (`checkins`, `checkin_demand_restrictions`). `New(level, demands)` is the one validating, de-duplicating constructor of a `CheckIn` (`ErrInvalidLevel`, `ErrUnknownDemand`); the handler and `Save` trust it, and the SQL `ON CONFLICT DO NOTHING` stays as a safety net. `Save(tx, residentID, date, CheckIn, now)` upserts on `(resident_id, checkin_date)` and replaces the day Restrictions; `LoadMany(q, residentIDs, date)` reads each Resident's Check-in in the caller's snapshot (a Resident with none is absent); `Store.Get` is the single read for the route. Day Restrictions are never written to the lasting `user_demand_restrictions`. |
| `streak` | The Streak rule, pure (`streak.go`, stdlib and `allocation.Date` only; `purity_test.go` enforces it for every file but `handler.go` and `store.go`). `Day` holds a Resident's facts for one Home-local date (`Completions`, `Undone`, `Drained`); `Judge(Day)` returns `Grow`, `Pause` or `Break`; `Current(days, today)` walks the final days back from yesterday (grow adds one, pause carries on, break stops) and adds today only when it already grows, returning the number and `todayGrew`. Today is passed in, never read. Table-tested with explicit dates; the fake-clock tests are at the API seam. The rules are in [Daily Allocation](allocation.md). |
| `streak` (store) | `store.go`: `Store.Current(ctx, residentID, today)` reads the facts for one Resident in a single aggregated query over `task_residents` (left-joined to `completions` on the same date for `undone`), `completion_residents` and Drained `checkins`, up to today, and hands them to `Current`. Nothing is stored and there is no new table or migration. |
| `dayplan` | Runs Allocation and stores and reads the Day Plan. `Planner` (built with `New(db, Allocator, logger, ...Option)`; `WithNudger(n)` sets the optional `Nudger` interface (`DayPlanReady`, `CheckinReminders`) that `RunDue` calls after planning every due Home, first for the Homes planned in this tick, then the reminders, inside a recover and under one shared 30s context deadline (`WithNudgeTimeout` changes it, for tests); no option means no push, and `dayplan` never imports `push`; an allocator names itself in the run record through `Name()`; `WithLLM(proposer, dailyCap, timeout)` adds the optional `Proposer` interface (`Name`, `Propose(ctx, State)`), which `PlanHome` asks first, under a daily cap per Home (`llmcap.go`, reserved on the pool before the call) and one LLM budget per tick (20s, `WithLLMBudget` for tests), falling back to the `Allocator` with a stable `fallback_reason` when the call fails or `Check` refuses its plan; Check-in and "right away" re-plans never ask it; the same `LLMConfig` carries the optional `Explainer` interface (`Explain(ctx, []explain.ResidentFacts)`) and its `ExplainBudget`, 15s by default, which `RunDue` uses in `explainHomes` (`dayplan/explain.go`) after planning every due Home and before the nudges: one call per Home, reserved on the same daily cap, best effort and inside a recover) has `DueHomes(now)`, `PlanHome(homeID, now)` and `RunDue(now)`. `DueHomes` converts `now` to each Home's IANA zone and returns the Homes whose local wall-clock time is at or past their Allocation time and that have no run for the local date ("at or past", so a late tick or a daylight-saving gap still plans once); a Home with an unknown zone is logged and skipped. `PlanHome`, `PlanResident` and `CheckIn` all run through one private opener, `Planner.inHomeTx` (`tx.go`): Begin, lock the Home row (`FOR NO KEY UPDATE`, `lockHome`, which returns the Home's `homeClock`, its local date and zone, the only date a run uses), the caller's steps, Commit, rollback by `defer`. The planning paths call it through `refreshedHomeTx`, which runs `tasks.RefreshIn` through the same transaction for that date before the caller's steps; the Home lock comes before the Chore locks, and a Refresh failure fails the run (a Check-in included). The actions use `inHomeTx` as it is, with no Refresh. A run that finds nothing to write (the day is already planned) returns nil and commits the Refresh, which is idempotent; `PlanHome` writes the run in a savepoint so a unique violation does not abort the transaction. Rows of `day_plan_assignments` are written only by `insertAssignments` (`state.go`), which `store`, the Check-in re-plan and `Take` call. `PlanHome` (with the LLM off) goes straight into that transaction: it looks for the run, loads the `allocation.State` (all open Tasks, overdue ones included, joined with their Chore for Demands, people and allowed weekdays; Residents with Energy and both levels of Restriction), asks the Allocator, has `allocation.Check` referee the proposal, and writes the run and the assignments. A proposal that errors or breaks any rule is never stored as a plan: the run is recorded `rejected` with the violations, nothing is assigned, the rejection is logged, and the day is taken, so it is not retried until tomorrow. With the LLM on, `PlanHome` first looks at the Home in a short `refreshedHomeTx` of its own (it returns `AlreadyPlanned` if the day has a run, otherwise it refreshes and reads the State the model is shown), calls the model with no lock and no connection held, then plans in the main transaction, which throws the answer away if the Home's date changed meanwhile. Refresh uses the transaction's connection, so a call holds one connection at a time (with `DB_MAX_CONNS=2`). The run's `reasons` hold the pool, each Resident's Energy and any violations or error; the assignments are rows of `day_plan_assignments` only, and an old run whose `reasons` still carries `assigned` reads the same (the key is ignored and goes the next time the reasons are written). Energy is the Resident's Baseline points for the weekday of the Home's local date, scaled by their Check-in when they made one, in one function (`energyOn`); an unset day is 0 and gives that Resident nothing, even with a Check-in. The Check-in's day-only Restrictions are added to the general Demand Restrictions. A two-person Task is stored as one `day_plan_assignments` row per Resident; `Store.Today` lists it under each holder with `with`, `Complete` records every holder, `Refuse` frees both while nobody accepted, and re-plans keep or release both rows together (see [allocation](allocation.md)). The `Check` violation kinds are `over_energy`, `broken_restriction`, `unknown_task`, `duplicate_task`, `unknown_resident`, `weekday_not_allowed` and `wrong_resident_count`. `CheckIn(homeID, residentID, CheckIn, now)` stores a Check-in and, when today's run is `planned`, plans that one Resident again in the same transaction (same Home lock and Refresh as `PlanHome`, so a Task that came due after the plan is a candidate; see [allocation](allocation.md)); with no run it only saves, after a `rejected` run it only saves, and a failed or refused re-plan rolls everything back and returns an error. `PlanResident(homeID, residentID, now)` is "get my tasks right away": it locks the Home, refreshes the Tasks, and plans that one Resident from the pool through the same re-plan path as a Check-in (`replanRun`); with no run for the date it creates today's run first, which makes the job skip the Home today (see [allocation](allocation.md)); after a `rejected` run it changes nothing and returns `Rejected`; a failed or refused proposal rolls back and returns an error. Swaps (`swap.go`) are `OfferSwap`, `AcceptSwap`, `DeclineSwap` and `CancelSwap`, run through the same `act` wrapper (Home lock, today's run), with `acting.mayDo` (the referee call Take also uses) deciding both sides, the assignment rows moving in `moveCommitment` (the reasons hold no assignments, so nothing is rewritten) and the sentinels `ErrNotHeldByOther`, `ErrSwapPending`, `ErrSwapNotFound`, `ErrSwapClosed`, `ErrSwapStale` and `ErrRecipientDrained` (see [allocation](allocation.md)); `Store.Today` adds the caller's live offers as `swaps`. The Day Plan actions are `Accept`, `AcceptAll`, `Refuse`, `Take` and `Complete` (`commit.go`): each runs through `act`, which uses the same opener as the job (Home lock, no Refresh), loads today's run with `loadRun`, acts, and commits; every early return rolls back. Accept, AcceptAll, Refuse and Take need a `planned` run (`ErrNoPlanToday`); Complete without one is `ErrNoPlanToday` too. A Complete on a pool Task runs `acting.takeFromPool`, the body Take shares. The Task row is locked `FOR UPDATE`, joined to its Chore on `home_id`, so a Task of another Home is `ErrTaskNotFound`. Errors are sentinels (`ErrTaskNotFound`, `ErrNoPlanToday`, `ErrNotProposed`, `ErrAlreadyCommitted`, `ErrNotInPool`, `ErrNotYours`, `ErrAlreadyDone`, `ErrTwoPersonTask`, `ErrRestricted`, `ErrDrained`); `dayplan` knows no status codes. `Take` runs `allocation.Check` on a plan of only that Task and ignores the over-Energy violation. `LocalDate(zone, now)` and `lockHome` both build on `clockIn`, the one place a zone becomes the Home's local date. The server builds its own `Planner` from `Deps.Allocator` (default `allocation.Baseline`), which must be the one the job uses. `RunDue` plans each due Home and logs, but survives, a failure for one; it returns a `Summary`. `Store.Today` reads the stored plan for the API and never plans or refreshes; it reports the run's `id` (as `runId`), its `allocator` and its stored `fallback_reason` (as `fallbackReason`, absent when null). `RunDue` and `ReplanHome` end in one private step, `finishPlanned` (explanations, then nudges); only the tick passes `plannedAndReminders` (a `nudgeScope`; the replan passes `plannedOnly`), so a replan never sends Check-in reminders to other Homes. `ReplanHome(homeID, now)` is the staging-only replan: in its own `inHomeTx` it deletes the Home's run for the local date (assignments and explanations cascade) and that Home's `day_plan_ready` rows in `nudges`, commits, then plans through the normal `planHome` (LLM budget included), explains and nudges as a tick does. It never touches `llm_calls`, so the daily cap still applies, and it leaves Commitments (`task_residents`) in place. `EventsHandler(p, clock, log, ...EventsOption)` is the job Lambda's HTTP surface. It serves two events on `POST /events`: the EventBridge scheduled event, and, only with `WithReplan()`, the replan event (`source` `homeowner.dev`, `detail-type` `Replan Home`, `detail` `{"homeId": "<uuid>"}`, built with `dayplan.NewReplanEvent`). `cmd/api` passes `WithReplan()` when `REPLAN_ENABLED` is true (`config.Config.ReplanEnabled`, default false; set on the staging Allocation function only). With the flag off, the replan event gets the same `400 unrecognised event` as any unknown event. A malformed `homeId` is `400`, an unknown Home `404`, any other failure `500`; success is `200 {"outcome"}`. Logs carry the Home id, date, allocator and counts only. |

## Request flow

The handler is a plain `http.Handler`, so the planned Lambda adapter can wrap it without changes. Middleware wraps the router from the outside in.

```mermaid
sequenceDiagram
    participant B as Browser (PWA)
    participant C as cors
    participant R as recoverPanics
    participant L as logRequests
    participant M as Router (ServeMux)
    participant H as healthz handler
    participant D as Postgres

    B->>C: GET /healthz (Origin header)
    C->>R: allowed origin gets CORS headers
    R->>L: a panic would become a 500 JSON error
    L->>M: one JSON log line per request, time from Clock
    M->>H: route match
    H->>D: Ping (2s timeout)
    D-->>H: ok
    H-->>B: 200 status ok
```

Unknown routes return `404` with `{"error":"not found"}`.

Authentication is not in that chain: `requireUser` wraps individual routes (like `push.Handler.RequireConfigured`), so `/healthz`, the VAPID key, CORS preflights and the 404 fallback stay open. It reads `Authorization: Bearer <token>` and asks the `Verifier`. A missing header, wrong scheme, malformed value or any verification failure gives the same `401 {"error":"unauthorized"}` with `WWW-Authenticate: Bearer`. With no Verifier it answers `503 {"error":"auth not configured"}` (fail closed). Otherwise it finds or creates the User, puts it in the request context (`identity.WithUser`), and calls the handler. The token is never logged.

An Invite token is also a credential, and it travels in the URL path of `/invites/{token}`. `logRequests` and the panic recovery log `loggedPath(r.URL.Path)`, which replaces that segment with `{token}`, so the raw path never reaches the logs. Any new route that carries a secret in its path must be added to `loggedPath`.

`requireResident` wraps `requireUser` for routes on a Home's data. It loads the caller's Home, puts the Membership in the context (`identity.WithMembership`), and answers `404 {"error":"no home"}` when the User lives in none, so a new User never gets a 500 and nobody can reach another Home's data. Every Home-scoped route goes behind it.

`httpx.DecodeBody` reads a JSON body with a caller-chosen size cap and an option to reject unknown fields. `cmd/api` imports `time/tzdata`, so `time.LoadLocation` works on Lambda and in distroless images.

## Routes

| Route | Behaviour |
|---|---|
| `GET /healthz` | Pings the database; `200 {"status":"ok"}` or `503`. |

Arrays are never `null`. Reasons are stable ids localised in the PWA. |

Invalid Home settings answer `400 {"error":"invalid home","fields":{...}}` with every bad field and a stable code each: `timezone` is `required` or `unknown` (not an IANA zone; `Local` is refused because it means the server's zone), `allocationTime` is `required`, `invalid` (not strictly `HH:MM`) or `not_quarter_hour` (the Allocator job runs every 15 minutes, so only minutes 00, 15, 30, 45). Every profile write answers `204` with no body, and every query uses the signed-in User's id, never one from the URL or body. Request bodies are capped at 4 KB and reject unknown fields (`httpx.DecodeBody` takes the cap and a strict flag; push keeps its 8 KB cap and lenient decoding).

The three `/push/*` routes answer `503 {"error":"push not configured"}` when no VAPID keys are set, so local development and CI need none. The two write routes need a signed-in User; `GET /push/vapid-public-key` stays public. Push configuration is checked first, then the token. Subscriptions carry `user_id`, and a test send reaches only a subscription the caller owns.

## The two test seams

A seam is the one place tests are allowed to push on the system.

```mermaid
flowchart LR
    T1["API tests (black box)"] -->|HTTP| S["server + real Postgres"]
    T1 -.-> F["fakes: Clock, Web Push, Cognito and the LLM client"]
    T1 -->|"RunAllocation"| P["dayplan.Planner, same database"]
    T2["Allocation tests (table-driven)"] -->|Plan, Check| A["allocation package"]
```

1. **The API.** `apitest.Start` runs the real server on a database cloned from a migrated template (`TEST_DATABASE_URL`), with a fake clock; `apitest.WithPush(key)` adds the recording fake Web Push sender, exposed as `App.Push`; `apitest.WithPhotos()` adds the in-memory `photos.Fake` (exposed as `App.Photos`) and the base URL `apitest.PhotosBaseURL`. `Start` always wires an `auth.Fake`; `App.SignInAs(email)` returns a client whose requests carry that fake's bearer token (the same email is the same User), and `apitest.WithoutAuth()` leaves the Verifier nil for the 503 case. `Client.JoinHome(t, homeID)` inserts a `residents` row for a signed-in User so tests can have several Residents without the Invite flow. `App.RunAllocation(t)` runs the Allocation job once at the fake clock's time over the same database, exactly as the scheduled tick does, and `App.UseAllocator(a)` swaps in a stub allocator (for example one the referee must reject). Tests assert on HTTP responses, never on internals, except the run record, which the job writes and only the database shows.
2. **Allocation.** Pure-function tests on `Plan` and `Check`.

There is no automated UI test; the web app is type-checked and built in CI.
