# The Go backend

Related: [ADR 0004](../adr/0004-ai-allocates-behind-a-deterministic-referee.md), [ADR 0002](../adr/0002-mirror-the-work-stack.md). Terms: **Allocation**, **Day Plan** in [GLOSSARY.md](../../GLOSSARY.md).

The backend is one Go module in `backend/`. In Go, code under `internal/` can only be imported from inside this module, and each folder is a *package*. `cmd/<name>/` holds a program's `main` function, an *entry point*.

## Entry points

| Entry point | Status | What it does |
|---|---|---|
| `cmd/api` | Built | `api` or `api serve` runs the HTTP server; `api migrate` applies database migrations and exits; `api vapid` prints a new VAPID key pair (a one-off human step, needs no database). |
| `api allocate` | Built | Runs the Allocation job once and exits: plans every Home whose Allocation time has arrived, then sends the push nudges when VAPID keys are set (for local runs and manual catch-up). |
| `cmd/evals` | Built | `go run ./cmd/evals` runs the manual allocator evals (baseline against the LLM allocator on synthetic days) and prints a comparison table; a separate binary, never in the API image and never run by `go test` or CI. See "Evals" in [Daily Allocation](allocation.md). |
| `api finance-events` | Built | The finance Lambda: serves only `POST /events` (the hourly scheduled event; any other body is `400`) and `GET /healthz`, and runs `finance.Syncer.Run`, then `finance.Reminders.Run` when the VAPID keys are set. Same image, a different command (ADR 0008). It connects to the database only when `FINANCE_ENCRYPTION_KEY` is set; without it the event is answered `200` and `finance sync disabled` is logged. See "The Transaction sync" below. |
| `api events` | Built | The Allocation job's Lambda: serves only `POST /events` (the scheduled tick that Lambda Web Adapter forwards) and `GET /healthz`. Same image as the API, a different command; see [ADR 0008](../adr/0008-scheduled-jobs-run-as-a-second-lambda-from-the-api-image.md). |

## Packages

The code is organised by domain ([ADR 0011](../adr/0011-split-each-domain-into-layer-folders.md)). Each domain package owns its data, its rules and its HTTP routes, and names its files by layer, so the same file name means the same job everywhere:

| File | Layer |
|---|---|
| `<package>.go` | The package doc, the domain model types and the sentinel errors (when the package has more than one file). |
| `handler.go` (`handler_<topic>.go` when one is not enough) | The HTTP controller: a `Handler` built with `NewHandler`, one method per route, which decodes the request, calls the domain and maps its errors to status codes. |
| `dto.go` | The named request and response shapes on the wire. Small inline body structs stay in the handler. |
| `store.go` | The repository: the only file that talks to Postgres. |
| any other file | The service: the domain's rules, for example `validate.go`, `resolve.go`, `schedule.go`, `commit.go`. |
| `handler_test.go` | The black-box API tests of that domain's routes, through the real server (`apitest`). |

Folders:

- `internal/<domain>/`: `users`, `homes`, `invites`, `chores`, `choresettings`, `catalog`, `profile`, `tasks`, `dayplan`, `checkin`, `streak`, `residents`, `push`, `photos`, `voice` (voice commands, see [Voice commands](#voice-commands) below), `finance` (the allowlisted Finances routes), `pluggy` (the Pluggy client, no routes), `admin` (the read-only operator API), plus the pure rule packages `allocation`, `schedule`, `onboarding` and the shared ids in `vocab`.
- `internal/identity/`: who is calling. The server's middleware puts the signed-in User and their Membership in the request context; handlers read them with `identity.CurrentUser` and `identity.CurrentMembership`, so no domain imports another just to know its caller. `users.User`, `homes.Home` and `homes.Membership` are aliases of its types.
- `internal/platform/`: code that knows no domain. `auth` (token verification), `clock`, `config`, `db`, `httpx` (`WriteJSON`, `WriteError`, `InternalError`, `DecodeBody`), the test harness `apitest` (it counts the SQL statements the API runs, `App.QueriesFor`, through a `pgx.QueryTracer` that `db.Connect` accepts as a pool-config option) and `puritytest`, the shared check behind every `purity_test.go`.
- `internal/server/`: the composition root. `server.go` builds every domain `Handler` and lists every route in one table; `auth.go` holds `requireUser` and `requireResident`; `boot.go` serves `GET /boot`, the home screen's launch reads in one response (below); `cors.go` and `http.go` the outer middleware.

Every domain handler also imports `identity`, `platform/httpx` and, where it needs the time, `platform/clock`; those arrows are left out. `allocation` imports nothing from the project and does no I/O (`purity_test.go` enforces that). `schedule` and `tasks` import it only for its `Date` type; `dayplan` is the only package that calls `Plan` and `Check`. The purity tests of `allocation`, `schedule` and `onboarding` cover the whole package; `catalog` exempts its `handler.go` and `checkin` its `store.go`, so the rule files stay pure next to their edge.

| Package | Role |
|---|---|
| `server` | Builds one `http.Handler` (`server.New(Deps)`): it constructs each domain's `Handler` and maps every route to one of their methods behind `requireUser` or `requireResident`. `Deps` holds everything outside the system that tests fake: database pool, clock, logger, CORS origins, the Web Push `Sender` and the public VAPID key, the token `Verifier` (nil means auth is off), the photo `ObjectStore` with `PhotosBaseURL` (nil means photos are off), and `Voice`, the `llmalloc.Client` behind voice commands, with `VoiceModel` (nil means voice is off; `cmd/api` sets an `llmalloc.NewAnthropic` client when `VOICE_ENABLED` is true). |
| `platform/config` | Reads `DATABASE_URL`, `MIGRATE_DATABASE_URL`, `PORT`, `MIGRATE_ON_START`, `DB_MAX_CONNS`, `CORS_ALLOWED_ORIGINS`, the optional pair `COGNITO_ISSUER` and `COGNITO_CLIENT_ID` (public identifiers, so plain environment variables; one without the other is an error, the issuer must be https, neither means auth is off), and the optional set `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (one key without the other is an error; neither means push is off). `VAPID_PRIVATE_KEY` is resolved from SSM through `VAPID_PRIVATE_KEY_SSM_PARAM`, like the database URLs. The LLM allocator settings: `LLM_ALLOCATOR_ENABLED` (default false; true needs `ANTHROPIC_API_KEY`, resolved from SSM through `ANTHROPIC_API_KEY_SSM_PARAM`), `LLM_MODEL` (default `claude-haiku-5-5`), `LLM_DAILY_CAP_PER_HOME` (default 3) and `LLM_TIMEOUT_SECONDS` (default 15), `VOICE_ENABLED` (default false; true turns on `POST /home/voice/interpret` and, like the allocator, needs `ANTHROPIC_API_KEY` or the API does not start; voice uses `LLM_MODEL` but not the allocator's daily cap or timeout) and the optional `LLM_MONTHLY_SPEND_LIMIT_USD` (a positive decimal of dollars with at most 6 decimals, stored as micro-USD in an `int64` as `LLMMonthlySpendLimitMicros`; unset is 0, shown as `null`). The limit is display-only: Terraform sets it on the API and on the job from one local, `GET /admin/ai` shows it against the month's estimated cost, and no code enforces it (the Anthropic Console does). Errors name the variable, never the key. The optional pair `PHOTOS_BUCKET` and `PHOTOS_BASE_URL` (one without the other is a startup error; the base URL must be https and is stored without a trailing slash; neither means the photo routes answer 503; `PhotosEnabled()`). `REPLAN_ENABLED` (default false) lets the Allocation function accept the replan event; only the staging Allocation function sets it. `FINANCE_ALLOWLIST` is the comma-separated emails that may use Finances (trimmed; `finance.NewAllowlist` lowercases; the placeholder `none` is skipped so it allows nobody, and an entry without an `@` is kept but logged as a warning); resolved from SSM through `FINANCE_ALLOWLIST_SSM_PARAM`, which stops the process if the parameter is missing or empty, so Terraform always creates it. `PLUGGY_BASE_URL` is where the Pluggy adapter calls (trimmed, no trailing slash, default `https://api.pluggy.ai`; it must be an http(s) URL or the API does not start). `ENVIRONMENT` names the deployment: `local`, `staging` or `production` (trimmed; unset or empty is `local`, anything else is a startup error). Terraform sets it on each API and Compose sets `local`; `GET /admin/me` returns it so the admin app can check it is talking to the environment it was built for. |
| `photos` | A User's photo. `ObjectStore` is the private-bucket seam (`PresignPut`, `Head`, `ReadPrefix`, `Copy`, `Delete`), nil in `server.Deps.Photos` when photos are off. `S3` is the real adapter over `aws-sdk-go-v2/service/s3`: `PresignPut` signs a PUT with `ContentType` and `ContentLength` set (both signed headers, so the upload binds the type and exact size) for 5 minutes with the API role's own credentials, so that role needs `s3:PutObject`; `Head` returns size, type and ETag and maps only S3's 404 to `ErrNotFound` (the API role holds `s3:ListBucket`, so a missing key answers 404); any other error, a 403 included, is wrapped and the handler answers 500; `ReadPrefix` is a ranged GET of 16 bytes; `Copy` is `CopyObject` with `MetadataDirective: REPLACE`, the content type, `Cache-Control: public, max-age=86400, immutable` and `CopySourceIfMatch` set to the ETag `Head` returned, so an object replaced after the checks answers 412, which is `ErrChanged` and a `400 invalid_object` from Confirm. `Fake` is the in-memory store for tests (`Upload` simulates the browser's PUT, `Objects`, `Presigned`, `FailDelete`). `keys.go` holds the pure rules: `NewPendingKey(userID)` is `pending/<userID>/<22 chars of 128 random bits>`, `NewAvatarKey(ext)` is `avatars/<fresh id>.<webp or jpg>` (a fresh id, so a pending key and a public URL never link), `OwnsPendingKey` is a strict regex that includes the caller's id (how a User can only confirm a key issued to them, with no table), `Sniff` reads the magic bytes (JPEG `FF D8 FF`; WebP `RIFF` at 0-3 and `WEBP` at 8-11) and `URLBuilder` turns a stored key into `PHOTOS_BASE_URL/<id>.<ext>`, returning nil for a nil key or an empty base (`server.New` passes an empty base when `Deps.Photos` is nil). `Handler` serves the three routes behind `RequireConfigured` (`503 {"error":"photos not configured"}`). Confirm checks, in order, key ownership (`invalid_key`), existence (`not_found`), size and type (`invalid_object`) and magic bytes against the stored type (`not_an_image`), each a `400` that changes nothing; then copies to the avatar key, stores it and, only after that commit, deletes the pending object and the previous photo, best effort (a failure is logged at warn with the key and never fails the request). Magic bytes prove the type, not that the image decodes. |
| `push` | `Sender` interface (one `Send` per subscription, returning `ErrGone` when the push service answers 404 or 410), `WebPushSender` (real, on `webpush-go`, VAPID, 24h TTL, 10s HTTP timeout; it strips a leading `mailto:` from `VAPID_SUBJECT` because webpush-go adds one, and includes the push service's response body in non-2xx errors), `Payload` (`title`, `body`, `url` and an optional `kind`, `checkin_reminder`, `day_plan_ready`, `bill_due_today`, `bill_due_soon` or `bill_overdue`, that the service worker words for the device language; the English text is always sent too), `Store` (the `push_subscriptions` table: upsert, get, `ListByUsers` (all devices of a set of Users in one query), delete, and `Deliver`, which drops a subscription the push service rejected), and `Fake` for tests. |
| `platform/auth` | `Verifier` interface: a raw bearer token in, `Claims{Subject, Email}` out, or an error wrapping `ErrInvalidToken`. `Cognito` is the real one: RS256 only, signature from the pool's JWKS (fetched lazily on the first authenticated request, cached in memory for an hour, one refetch at most a minute for an unknown key id, old keys kept if a refresh fails, fail closed when none are known), `iss` equal to the issuer, `aud` equal to the app client, `token_use` equal to `id`, `exp` required, `email_verified` true, subject and email present. Time comes from the injected `Clock`. `Fake` mints tokens for tests and never touches the network. |
| `users` | `Store.FindOrCreate(sub, email, now)`: the single upsert behind the first-request-creates-the-User rule; it also returns `display_name` and `photo_key`, so every request's `identity.User` carries them. `Store.SetDisplayName` is one `UPDATE` that stores `NULLIF(name, '')`, so "" clears. `name.go` holds the pure rule `NormalizeName` (trim, "" when blank, 40 code points, no control or bidi characters), which answers `ErrNameTooLong` or `ErrNameInvalid`; `identity.ShownName` (display name, else the email before the last `@`) is shared with `homes`. `dto.go` holds `MeResponse`, whose `photoUrl` comes from the photo URL builder `Handler` is given. `Store.SetPhotoKey` and `ClearPhotoKey` are each one `UPDATE ... FROM (SELECT ... FOR UPDATE)` that returns the previous key, so two simultaneous confirms each get the right key to delete; `photos` uses them through its `Keys` interface (`users` never imports `photos`). |
| `onboarding` | The ordered step ids (`install`, `reminders`, `baseline`, `restrictions`, `preferences`, `home`, then `done`), `Valid` (what a client may `PUT`), `Next` (the step after the stored one) and `Before` (the stored values a step may move forward from). Stdlib only; `purity_test.go` enforces it. `users.Store.AdvanceOnboarding` applies the monotonic rule as one conditional `UPDATE`, and `homes.Store.Create` stores `done` in its transaction. |
| `homes` | `Membership{ResidentID, Home}` is a User's place in a Home: their own `residents` row and the plain `Home`. `Store.Create(userID, timezone, allocationTime, now, inHome)` inserts the Home and the first Resident in one transaction (and runs the optional `inHome` callback on it, which `POST /home` uses to add the reviewed Chores without `homes` importing `chores`) and maps the unique violation on `residents.user_id` to `ErrAlreadyResident`; `ForUser` returns the caller's `Membership` or `ErrNoHome`; `UpdateSettings` replaces the timezone and Allocation time. `LeaveTx(tx, residentID, homeID)` is the one place a Resident leaves a Home: inside the caller's transaction it locks the Home row (`FOR UPDATE`, so two last Residents leaving at once are serialised), deletes the `residents` row (the cascade clears their specific Preferences and Restrictions) and deletes the Home if nobody is left (the cascade clears its Chores, Tasks and Invites). Accepting an Invite uses it, and `Store.Leave(residentID, homeID)` wraps it in its own transaction for `DELETE /home/residents/me`. |
| `invites` | An Invite is a single-use link, valid while `now < expires_at` (`Validity`, seven days; at the exact instant it is expired). The token is 32 random bytes, base64url, shown once; only its SHA-256 is stored, and a token that is not canonical base64url of 32 bytes is `ErrNotFound` before the database is asked. `check` (pure) is the validity rule and `newToken`/`hashToken` are pure too. `Store.Create` caps a Home at `MaxOpenPerHome` (10) unused, unexpired Invites (`ErrTooManyOpen`), serialised by a `FOR NO KEY UPDATE` lock on the Home row. `Lookup` never writes. `Accept` is one transaction: claim the Invite with `UPDATE ... WHERE used_at IS NULL AND expires_at > now RETURNING home_id` (the single-use guard; on zero rows a read decides `ErrNotFound`, `ErrUsed` or `ErrExpired`), then if the User lives in the same Home `ErrAlreadyHere`, in another Home without `confirmLeave` `ErrWouldLeaveHome`, with it `homes.LeaveTx`, then insert the `residents` row (a unique violation is `homes.ErrAlreadyResident`). Any error rolls the claim back, so a failed join never burns the Invite. Imports `homes`, never the reverse. No HTTP types. |
| `profile` | `Store` for the User's profile: `Load`, `SetBaseline` (set some days, clear others, one transaction), `SetPreference` (neutral deletes the row), `AddRestriction`, `RemoveRestriction`. Writes are idempotent. `MaxBaseline` (20) is the named upper bound of a Baseline. |
| `chores` | `Validate(Input)` is pure: it trims the name, de-duplicates and sorts Demands and weekdays, and returns a stable code per invalid field, all at once (`Input` is decoded straight from the JSON body; numbers arrive as `any`, so a string or 2.5 is a field code, not a bad request; the first code recorded for a field wins). `Store` has `List`, `Create`, `Update`, `Delete`; every query that takes an id also filters on `home_id`, and a miss is `ErrNotFound`, and the handlers answer 404 for an id that fails `ValidID` without asking the Store. Imports `vocab` for Categories, Demands and Importances. `Chore` carries the JSON tags and is written to the response as is. |
| `catalog` | The fixed Catalog of common Chores and the rules that turn questionnaire answers into proposed Chores; Go code, no table, no migration. Pure (stdlib and `chores.Fields` only; `purity_test.go` enforces it). `Entries()` returns copies of the Catalog table in display order; each entry carries its own rule (how many Chores the answers call for, and an optional adjustment of Effort, interval or weekdays), so adding an entry is one place. An entry has a stable `ID` (for example `clean_bathroom`), `chores.Fields` with an English fallback name, and `PerRoom`. `Answers` is decoded like `chores.Input` (counts and weekdays as `any`); `ValidateAnswers` returns codes (`invalid`, `out_of_range`, `unknown`) keyed `rooms.bathrooms`, `outdoor.gardens`, `collection.trash`, `habits.cooking`, all at once; a missing section means none (cooking defaults to `sometimes`). `Propose(Answers)` is deterministic and follows Catalog order: a per-room entry yields one `Proposal` per room (`Instance` 1-based, `nil` when there is one), pets add `pets` Chores, a collection stream with days adds one weekly essential Chore limited to those weekdays, and habits change the Chores (a dishwasher swaps washing the dishes for loading it, no washing machine drops the laundry Chores, cooking `daily` makes the kitchen Chore heavier and more frequent). Outdoor areas are counts like rooms (`outdoor` is `{balconies, yards, gardens}`, kept apart from `rooms` so they never trigger the floor Chores), and every outdoor entry is `PerRoom`, so it is proposed once per area of its type (`sweep_yard` once per yard plus garden). Bounds: 0 to 10 rooms per type (kitchens 0 to 3), 0 to 10 areas per outdoor type and `MaxProposals` 125, which a test proves the largest answers (122) stay under. The API never renders a localised name; the PWA names a Chore from `catalogId` and `instance`. |
| `choresettings` | A Resident's Preference and Restriction on one specific Chore. `Resolve(Chore, General, Specific)` is pure and holds the rule: a specific Preference (neutral included) beats the general one for the Chore's Category, else neutral (source `specific`, `general` or `default`); Restrictions only add, so the reasons are the Chore's Demands that are in the User's general Restrictions plus the specific Restriction, listed apart. `Store` has `SetPreference`, `ClearPreference`, `AddRestriction`, `RemoveRestriction` (idempotent; the two sets prove in the same statement that the Chore is in the Resident's Home, the two deletes ask only when they removed nothing; `ErrNotFound` otherwise, the same for a missing Chore) and `Effective(homeID)`, which reads the Home's Chores, Residents, all their general profiles (`profile.LoadMany`, one `ANY($1)` query per profile table) and the specific rows in one read-only repeatable-read transaction, a fixed number of queries however many Residents there are. It has no HTTP types, so the Allocation job can reuse it; `allocation` is untouched. |
| `schedule` | `Decide(Chore, latest *Task, today)` is pure (stdlib and `allocation.Date` only; `purity_test.go` enforces it) and returns one decision: `Open` a Task with a window and Effort, `SetEffort` on the open Task, or `Nothing`. Rules (ADR 0001): a recurring Chore has windows of N consecutive days, the first starting on the day it was created in the Home's zone; `WindowStart` and `WindowEnd` are inclusive dates. With allowed weekdays, the window starts on the first allowed day on or after the scheduled start and N is rounded up to whole weeks, so a Task only opens on an allowed day. A one-off Chore gets one Task, ever (a day, or a week when weekdays are limited). A window is missed when today is past `WindowEnd` and the Task is still open; the same Task stays open and keeps its window. Missed windows are derived (`floor((today - WindowStart) / length)`), never counted, so repeated or skipped runs agree; a recurring build-up Chore's current Effort is `min(5, base + missed)`, other Chores stay at base (`buildsUp` is ignored on a one-off). After a Task is done, the next window of a recurring Chore starts N days after `closed_on` at base Effort (an assumption until a Completion ticket defines it). |
| `tasks` | `RefreshIn(ctx, tx, homeID, date, loc, now)` brings a Home's Tasks up to date inside the caller's transaction, for the date and zone the caller already worked out: it sets `statement_timeout` to 5s with `SET LOCAL`, locks each Chore row `FOR UPDATE`, loads its latest Task, applies `schedule.Decide` and writes, then puts back the value it read first with `set_config('statement_timeout', ..., true)`, so the rest of the caller's transaction keeps its own setting, the session's or a `SET LOCAL` of its own (`SET LOCAL` lasts until the transaction ends). The Chore row locks are held until the caller commits, so a concurrent `GET /home/tasks` waits for a Day Plan run, which is short. `Store.Refresh(homeID, now)` is the pool wrapper for callers outside a run (`GET /home/tasks`): it opens a transaction, converts `now` to a date in the Home's IANA zone (an unloadable zone is an error, never UTC), calls `RefreshIn` and commits. Idempotent and safe in parallel; the partial unique index on open Tasks is the final guard and the insert is `ON CONFLICT DO NOTHING`. `Store.ListOpen(homeID)` returns the open pool, never nil. `dayplan` calls `RefreshIn` from its one transaction opener before it builds `allocation.State`. |
| `checkin` | The Check-in rule, pure (`checkin.go`, stdlib only; `purity_test.go` enforces it for every file but `store.go`). `Level` (`drained`, `low`, `normal`, `energized`) with `Valid`, and `Scale(base, Level)`: 0, 50%, 100%, 130% of the Baseline in whole points, rounded down (integer arithmetic), 0 for a base of 0 or an unknown level. Table-tested for every level and every base 0 to `profile.MaxBaseline`. Demand validation stays in `vocab.IsDemand`. |
| `checkin` (store) | `store.go` stores Check-ins (`checkins`, `checkin_demand_restrictions`). `New(level, demands)` is the one validating, de-duplicating constructor of a `CheckIn` (`ErrInvalidLevel`, `ErrUnknownDemand`); the handler and `Save` trust it, and the SQL `ON CONFLICT DO NOTHING` stays as a safety net. `Save(tx, residentID, date, CheckIn, now)` upserts on `(resident_id, checkin_date)` and replaces the day Restrictions; `LoadMany(q, residentIDs, date)` reads each Resident's Check-in in the caller's snapshot (a Resident with none is absent); `Store.Get` is the single read for the route. Day Restrictions are never written to the lasting `user_demand_restrictions`. |
| `streak` | The Streak rule, pure (`streak.go`, stdlib and `allocation.Date` only; `purity_test.go` enforces it for every file but `handler.go` and `store.go`). `Day` holds a Resident's facts for one Home-local date (`Completions`, `Undone`, `Drained`); `Judge(Day)` returns `Grow`, `Pause` or `Break`, by precedence: a Completion grows, otherwise an undone Commitment on a non-Drained day breaks, otherwise pause ([ADR 0014](../adr/0014-a-day-with-any-completion-keeps-the-streak.md)); `Current(days, today)` walks the final days back from yesterday (grow adds one, pause carries on, break stops) and adds today only when it already grows, returning the number and `todayGrew`. Today is passed in, never read. Table-tested with explicit dates; the fake-clock tests are at the API seam. The rules are in [Daily Allocation](allocation.md). |
| `residents` | `GET /home/residents` and `GET /home/residents/{id}`. The detail read: `handler.go` `Get` rejects a malformed id with `chores.ValidID` before any store call, then `Store.Find` (one query, scoped to the caller's Home), `streak.CurrentFor` for that one id (the same call as the list and `GET /home/streak`), and `Store.CompletionsBetween` (the Completions the Resident is on over `today-29 ..= today`, then one query for the partners, skipped when there are no Completions), grouped into days in Go while scanning ordered rows. A Chore deleted later takes its Completions with it, from the history and the Streak alike. `store.go`: `Roster(homeID, callerResidentID)` is one query joining `residents` to `users` (caller first, then `created_at, id`); email and user id are read only to compute the name and the avatar. `handler.go`: `List` computes `today` once with `dayplan.LocalDate`, calls `streak.CurrentFor` with every roster id (two queries in all, plus the middleware's lookups) and builds the response. `dto.go` is the privacy boundary: dedicated structs, no embedded User, profile, Check-in or Day Plan type. It imports `streak`, `users` (`Initials`, `AvatarTone`), `dayplan` and `identity`; nothing imports it. `move.go` serves `PATCH /home/completions/{id}` (`Handler.MoveCompletion`): it lives here because its `200` is `detail`, and `dayplan` cannot render that without an import cycle. ## Request flow

The handler is a plain `http.Handler`, so the planned Lambda adapter can wrap it without changes. Middleware wraps the router from the outside in.

```mermaid
sequenceDiagram
    participant B as Browser (PWA)
    participant C as cors
    participant R as recoverPanics
    participant L as logRequests
    participant M as Router (ServeMux)
    participant H as healthz handler
    participant D as Postgres

    B->>C: GET /healthz (Origin header)
    C->>R: allowed origin gets CORS headers
    R->>L: a panic would become a 500 JSON error
    L->>M: one JSON log line per request, time from Clock
    M->>H: route match
    H->>D: Ping (2s timeout)
    D-->>H: ok
    H-->>B: 200 status ok
```

Unknown routes return `404` with `{"error":"not found"}`.

Authentication is not in that chain: `requireUser` wraps individual routes (like `push.Handler.RequireConfigured`), so `/healthz`, the VAPID key, CORS preflights and the 404 fallback stay open. It reads `Authorization: Bearer <token>` and asks the `Verifier`. A missing header, wrong scheme, malformed value or any verification failure gives the same `401 {"error":"unauthorized"}` with `WWW-Authenticate: Bearer`. With no Verifier it answers `503 {"error":"auth not configured"}` (fail closed). Otherwise it finds or creates the User, puts it in the request context (`identity.WithUser`), and calls the handler. The token is never logged.

An Invite token is also a credential, and it travels in the URL path of `/invites/{token}`. `logRequests` and the panic recovery log `loggedPath(r.URL.Path)`, which replaces that segment with `{token}`, so the raw path never reaches the logs. Any new route that carries a secret in its path must be added to `loggedPath`.

`requireResident` wraps `requireUser` for routes on a Home's data. It loads the caller's Home, puts the Membership in the context (`identity.WithMembership`), and answers `404 {"error":"no home"}` when the User lives in none, so a new User never gets a 500 and nobody can reach another Home's data. Every Home-scoped route goes behind it.

`GET /boot` (`server/boot.go`, behind `requireUser`) answers `200 {"sections": {"<key>": {"status", "body"}}}` once the caller is signed in. Each key is the exact path the PWA requests (`/me`, `/me/onboarding`, `/demands`, `/home`, `/home/day-plan`, `/home/check-in`, `/home/streak`, `/home/residents`, and for the allowlist `/me/finance`, `/me/finance/bills?month=M`, `/me/finance/commitments?from=M`, `/me/finance/savings`, `/me/finance/bill-suggestions`). Each section runs the route's own handler in its own goroutine against a recorded request, so `body` is byte for byte the endpoint's answer. A goroutine recovers its own panic into a `500 {"error":"internal error"}` section, and every failed section is logged with its key and status, so one failure never fails the response. The gates are shared with the guards, not copied: `residentScope` (used by `requireResident`) gives every resident section `404 no home` or 500, and `financeGate` (used by `requireFinance`) leaves every finance section out off the allowlist and makes them `503 finance not configured` with no key. The bills and commitments sections need `?month=YYYY-MM` from the caller and are left out without it; a malformed month is the handlers' own 400. `/push/vapid-public-key` is not a section.

`requireFinance` guards the Finances routes (`server/finance.go`). It wraps `requireUser`, so authentication comes first (401 for no or a bad token) and the allowlist is the authorisation: it answers `403 {"error":"forbidden"}` unless the lowercased, verified email of the caller is in `Deps.FinanceAllowlist`, and always when the list is empty or missing. `financeMux()` holds the routes (the `/me/finance` routes in the route table; `GET /me/finance` is served by `finance.Status`) and `server.New` registers it behind the guard once, for both `/me/finance` and `/me/finance/`, so an unknown subpath meets the allowlist first: 403 for an outsider, 404 for an allowed User. The refusal is logged with the path only, never the email. The list comes from `FINANCE_ALLOWLIST`, resolved from the SSM `StringList` `/homeowner/<env>/finance-allowlist` through `FINANCE_ALLOWLIST_SSM_PARAM` and read once at start-up (a change applies at the next cold start; see `docs/development.md`). `GET /me` and `PUT /me/name` carry the same answer as `finance`, through the `func(email string) bool` that `users.NewHandler` takes (`finance.Allowlist.Allows`), so `users` does not import `finance`. The `finance` package holds the `Allowlist` type and the status handler. The Terraform placeholder `none` is skipped, so it allows nobody.

**The Pluggy client.** `internal/pluggy` holds the `Client` interface (`Auth`, `CreateConnectToken`, `GetItem`, `ListAccounts`, `ListTransactions`, `ListBills`) and the few types the app uses; `NewHTTP(baseURL)` is its only implementation, a plain `net/http` client with a 10-second timeout and no SDK. It sends the API key in `X-API-KEY`, caps each decode with `io.LimitReader`, never logs, and its errors carry the operation and the status only (`pluggy: list transactions: status 502`), with `ErrUnauthorized` for 401/403 and `ErrNotFound` for 404. Money is decoded as `json.Number` and converted to centavos by an exact string parser, never through `float64` (more than two decimals is refused). `ListTransactions` calls `GET /v2/transactions?accountId=&dateFrom=&dateTo=` (the v1 `GET /transactions` answers 410 and is removed on 2026-12-31), which pages by cursor: a page carries `Next`, the query string Pluggy gave back, empty on the last page, and the caller passes it back as the cursor. Direction comes from the sign of the amount, never `type` (on a credit card Pluggy sends a purchase positive and a bill payment negative), and rows are keyed on Pluggy's `id`, because `providerId` is often missing. A row with `paymentData` carries a `Counterpart` (`pluggy.Party`, a name and a document): the receiver when the amount is negative, the payer when positive. `ListAccounts` also reads the account holder (`owner`, `taxNumber`; empty on a card). A `Party` lives in memory only: the sync reduces it to one boolean and never stores or logs it. `ListBills` calls `GET /bills?accountId=&pageSize=500` for a card account and returns each bill's id, closing date, due date, total in centavos and currency (`financeCharges` and `payments` are ignored; `shortcut:` one page of 500, follow `totalPages` if a card ever has more). `pluggytest` (a separate package so its embedded fixtures never reach the production binary) starts an `httptest` server that replays the sandbox capture in `testdata/sandbox/`, with a synthetic second page for the checking account to test following `next`, and `Fail(path, status)` to force failures; only `apitest` and the adapter's own tests import it. `apitest.WithPluggy()` wires `Deps.Pluggy` to the real adapter over that fake and exposes it as `App.Pluggy`.

After the allowlist check, `requireFinance` fails closed: with no `Deps.FinanceKey` every finance route answers `503 {"error":"finance not configured"}`. An outsider still gets 403 and learns nothing. The key is `FINANCE_ENCRYPTION_KEY` (base64 of 32 bytes), read from the SSM `SecureString` `/homeowner/<env>/finance-encryption-key` through `FINANCE_ENCRYPTION_KEY_SSM_PARAM`. It is an `optional` entry in `secretParams` (`cmd/api/secrets.go`): a failed read logs `finance disabled: encryption key unavailable` with the parameter name and leaves the variable empty, so a key a human has not created yet disables Finances and not the API. `config.Load` decodes it; empty or not exactly 32 bytes gives a nil `Config.FinanceKey` and a warning, never an error.

**The seal flow.** `finance.Seal` (`finance/seal.go`, standard library only) encrypts with AES-256-GCM under a fresh 12-byte `crypto/rand` nonce and returns `version(1) || nonce || ciphertext+tag`. The additional authenticated data is `userID + "|" + field` (`client_id` or `client_secret`), so a blob copied to another User's row, or a Client ID moved into the Secret column, fails to open. `finance.Open` answers one detail-free error, `ErrOpen`, for a short blob, an unknown version byte or any authentication failure. `PUT /me/finance/credentials` trims both values (1 to 200 characters, no control characters, else `400 {"error":"invalid credentials","fields":{...}}`), seals each and upserts the row, answering 204. `DELETE` answers 204 whether or not a row existed. `GET /me/finance` reports `configured` from the row's existence and never decrypts. Credentials are opened only in memory, just before Pluggy's `/auth` call (#424), and no error, log line or response carries the key, a plaintext or a ciphertext. Encryption at rest protects a leaked database or backup; it does not protect against someone who can read both the database and the SSM key, or against the running API.

**The Transaction sync** (`finance/sync.go`, `rules.go`, `events.go`). `Syncer.Run(ctx, now)` picks the Items with credentials whose import is unfinished or whose last sync is older than 24 hours (longest-waiting first, `last_synced_at NULLS FIRST`), keeps those whose User's email is still on the allowlist, and works until its budget (60 seconds; tests set it with `apitest.WithFinanceSyncBudget`) leaves less than 10 seconds. It opens each User's credentials once and calls Pluggy `Auth` once. Per Item it first reads the accounts again (`ListAccounts`) and fills a card's bill days (`SetBillDays`) only when the card has neither day yet, so days the User typed stay; Pluggy's two days count only as a pair (`pluggy.HTTP.ListAccounts` reports a lone day as none). Then, for each card Source, it reads the bank's bills (`ListBills`) and upserts the BRL ones into `finance_card_bills` (`Store.UpsertCardBills`, on `(source_id, provider_id)`, so a corrected bill is updated). A failure there is logged (`step` `card bills`) and skipped, never failing the Item: a connector may not support `/bills`, and the card then keeps the computed bill ([ADR 0021](../adr/0021-a-closed-card-bill-takes-the-banks-total.md)). The Item's owner is the first account with a holder name or CPF. Per Source it reads windows of at most one month through `GET /v2/transactions`, following the cursor `next` of each page, from the day after the Source's `import_cursor` (at most 12 months back) to today; each page is one `INSERT ... ON CONFLICT (source_id, provider_id) DO UPDATE` over `unnest` arrays, and the cursor moves to the window's end after the window. At least one round always runs, so a tiny budget still makes progress. When every Source has reached today the Item gets `import_complete = true` and `last_synced_at = now`; afterwards each daily sync re-reads the last 45 days in one window, because rows post late: a card charge can reach the feed weeks after it posted, and the window covers a whole open bill. A window cut off is read again next run, which the upsert makes harmless. After the imports, and before categorizing, each User with an Item finished this run has their Bills paid from the bank: `Store.PayBillsFromBank` loads the Bills, every payment row (undone ones included, as taken) and the unlinked Expenses of the previous and current São Paulo months, runs the pure `MatchBills` (`rules.go`: Expense only, `-amount_cents` equal to the expected amount, the folded Bill name of 3 or more characters contained in the folded description, the posted month is the Bill's month; the longest name wins a Transaction, the earliest Transaction wins a Bill-month) and inserts `paid_by = 'bank'` rows with `ON CONFLICT DO NOTHING`, so a repeated sync adds nothing. A Transaction the User later retypes as a Transfer keeps its payment.
 "Today" and every `posted_on` are São Paulo dates (`postedOn`): Pluggy's timestamps are UTC and the User has no zone. `provider_id` is Pluggy's transaction `id` (its `providerId` is missing on real rows). Direction comes from the sign of the amount, never Pluggy's `type`. On a `credit_card` Source the sync first negates the amount (`toRows`), so `amount_cents` stays signed from the Source's point of view. Negative is an `expense` (its Spending Category is set as below), otherwise `income`. `toRows` also sets `own_counterpart` when the row's counterpart is the Item's owner (`sameParty`: the CPF digits decide when both have the same number of digits, else the folded names; empty values never match; `shortcut:` a masked document falls back to the name). A card row never has one, because the sign flip inverts which side Pluggy named. An account's `PENDING` rows and non-BRL rows are skipped (the latter counted in `Summary.SkippedCurrency`); a card keeps its `PENDING` rows, because its charges stay pending until the bill closes and Pluggy keeps the `id` when they post (`shortcut:` a pending charge Pluggy deletes and re-creates stays stored twice); a foreign card charge is stored in reais when Pluggy sends `amountInAccountCurrency`, and skipped and counted when it does not. Some banks send every installment of a new card purchase on the purchase day; `toRows` moves each one numbered above the lowest of its group (same merchant key, total and day) on by the difference in months (`moveInstallment`), so a bill counts only its own. An upsert keeps a `type` whose `type_set_by` is `user`, and keeps the category of a row whose `category_set_by` is `user` or `auto` or whose type the User set. `MerchantKey(description)` is the pure key later rules reuse: uppercase, accents folded, `PARC nn/mm`, digits and punctuation removed.

**Classification** (`Classify` in `rules.go`, pure). After each page is stored, `Syncer.classify` reads the User's `auto` rows over twice the transfer window around the page (`ClassifyInput`) and the stored card bills due in that span (`CardBillsDue`), and writes back only rows whose type or category changed. A row the User typed is never changed nor used as a partner. The rules, first match wins:

1. **Saving.** A merchant key starting `APLICACAO` (either sign), or a positive `RESGATE`, is `saving`, and is left out of the pairing below. `shortcut:` the credit half of an Aplicação on a savings Source is Income; the User can correct it.
2. **Bill phrases.** A merchant key containing `PAGAMENTO FATURA`, `PAGAMENTO DE FATURA`, `PAGAMENTO RECEBIDO`, `PAGAMENTO ON LINE` or `PAGAMENTO ONLINE` is a `transfer`.
3. **Bill amount.** On a Source that is not a card, a BRL debit equal to a stored bill's `total_cents` and posted within `transferWindowDays` (3) of its due date is a `transfer`: the payment of that bill.
4. **Own counterpart.** A row with `own_counterpart` is a `transfer`, with or without a partner.
5. **Pairing.** A debit and a credit of the same amount and currency on two Sources within 3 days are both `transfer`s.
6. **Sign.** Any other credit on a card is an Expense (a refund); any other credit is `income`, any other debit `expense`.

Rules 2 to 4 all give a Transfer, so their order only matters for the reader; rule 1 beats them all. Migration `0042` restarted every import, so all 12 months were read again and classified with rule 4.

**Bill reminders** (`finance/reminders.go`, the rule `DueReminders` in `rules.go`). In the same hourly event, after `Syncer.Run` (and even if the sync failed), `Reminders.Run` reads every Bill of an allowlisted User, with the zone of the User's Home (`residents` `LEFT JOIN homes`) or `America/Sao_Paulo`, and the months already paid (an undone payment does not count). The pure rule works on the User's local clock: nothing before 09:00 local (`ReminderQuietUntilHour`); an unpaid Bill whose due date (`DueDate`, month-end clamped) is today is `bill_due_today`, tomorrow `bill_due_soon`, earlier in the month `bill_overdue`; earlier months are never reminded. It then follows the `nudges` pattern: only Users with a device are claimed (a User has notifications off exactly when they have no `push_subscriptions` row), a `finance_bill_reminders` row `(bill_id, month, kind)` is claimed with `INSERT ... ON CONFLICT DO NOTHING RETURNING`, only claimed rows are sent, one push per User and Notice (two Bills due tomorrow give one `bill_due_soon` push) through `push.Store.Deliver` (5s per send, gone devices pruned), and the outcome (`delivered`, `failed`, `gone`) is recorded on every row the push covered, detached from the run's context. The ledger kind is `due_soon` (today and tomorrow share it) or `overdue`, so a Bill gets at most one of each per month; delivery is at most once. The Payload is generic English plus the Kind, with no Bill name and no amount, and `url` `/finances`. `DELETE /me/finance` clears the ledger (`finance_bill_reminders` is in `financeTables`). Tests run it with `App.RunFinanceReminders` over the fake Web Push sender.

 **Spending Categories** (`finance/categorize.go`): only Expenses get one. The order of decision is the User's saved correction (`finance_merchant_categories`, joined in the upsert), then Pluggy's category through the fixed map `pluggyCategories` (`rules.go`), both `auto`; an Expense nothing decides is `other`/`fallback`. After the imports, `Syncer.categorize` visits every allowed User with a `fallback` Expense (not only those just synced): it applies late corrections, and with a Categorizer (`WithCategorizer`, built by `finance-events` only when `ANTHROPIC_API_KEY` is set) sends the distinct `merchant_key`s in batches of 100, each call reserved first in `finance_llm_calls` (10 a day per User, São Paulo date, single-statement pattern of `dayplan.reserveLLMCall`). A merchant the model leaves out, a past-cap batch or a failed call stays `fallback` and is tried again on a later run. Each attempt writes one best-effort `llm_call_events` row (`service = 'categorizer'`, no Home, no run, no User). A failure (rejected credentials, a Pluggy 5xx) is logged and the run moves on; the Item's `last_synced_at` does not change, so the next hourly run retries it. Logs carry counts and ids only; a test captures the logs of a full and a failing sync and asserts no description, amount, Pluggy id, credential or API key appears. Two overlapping runs are safe (idempotent upserts, no advisory locks, which PgBouncer's transaction mode would break), and rows are inserted by `source_id` only, so a concurrent delete of the Source fails the foreign key instead of bringing data back. Tests drive it with `App.RunFinanceSync` through the real adapter against `pluggytest`.

`requireSuperAdmin` guards the operator API ([ADR 0017](../adr/0017-operate-through-a-separate-admin-app-per-environment.md)). The `/admin/` routes are listed in one table in `server/admin.go` and registered on a sub-mux that `server.New` wraps once: `mux.Handle("/admin/", requireSuperAdmin(adminMux))`. The guard verifies the token like `requireUser` (401 for none or a bad one, 503 with no Verifier), then answers `403 {"error":"forbidden"}` unless the token's `cognito:groups` claim (`auth.Claims.Groups`) contains `super-admin`. It never creates a User or loads a Home, and an unknown `/admin/x` meets the guard first, so only a super admin ever sees a 404 there. `GET /admin/me` returns the `environment` from `Deps.Environment` (the `ENVIRONMENT` setting: `local`, `staging` or `production`). A guard test walks the route table, so a new admin route is checked for 401, 403 and 200 without extra work. Membership of the group is granted by hand per environment; the app that calls these routes is described in [The admin dashboard](admin.md).

`httpx.DecodeBody` reads a JSON body with a caller-chosen size cap and an option to reject unknown fields. `cmd/api` imports `time/tzdata`, so `time.LoadLocation` works on Lambda and in distroless images.

## The month outlook and the leftover

The month outlook says what each month takes from the Monthly income, and so what is left: the **Leftover**. It is the rule `Outlook` in `finance/outlook.go`, pure (no database, HTTP or clock). `Handler.loadOutlook` gathers its inputs and is the one caller, so `GET /me/finance/commitments` (twelve months), `GET /me/finance/savings` (the current month) and the Committed figure of `GET /me/finance/transactions` cannot disagree.

```mermaid
flowchart LR
    SR["SpendRows: the months' rows, by CountsOn"] --> O["Outlook (pure)"]
    CS["CardSources: cards with their stored bills"] --> O
    IP["InstallmentPlans"] --> O
    MB["MonthBills: other Bills"] --> O
    BU["Budgets: Spending limits"] --> O
    LM["SpendRows of the 3 months before current, averaged by plannedBaseline"] --> O
    SS["SavingsSettings: Monthly contribution"] --> O
    IN["Income"] --> O
    O --> MO["MonthOutlook per month: cards, other Bills, installments off the card, planned, spent off the card, saving, total, leftover"]
```

For each month:

- **Card bills** (one line per card, even at zero). In the month today is in (`currentCardBill`), the line is the bill still to pay ([ADR 0024](../adr/0024-the-current-month-counts-the-card-bill-still-to-pay.md)): the latest closed bill (the bank's total) until it is paid (a debit off the cards of exactly that total, from its closing to three days past its due day, read as `StoredBill.Paid` by `CardSources`) or past due, then the open bill, the charges posted from that closing until the next typed one, or up to today without typed days (an installment a bank sent ahead past it, dated in its own month, counts there) plus installments still to be charged. Without bank bills, or when the typed closing is a week past the bank's latest, the typed days give the closing; a closed bill from typed days ends only on its due day. Later months leave out the charges that line holds. `loadOutlook` reads rows up to `billLead` months past the current month, so a one-month read (Committed, Savings) holds the same open bill. In every other month, when the bank reported a bill due in the month, the line is that bill's `total_cents` ([ADR 0021](../adr/0021-a-closed-card-bill-takes-the-banks-total.md)); its installments are not added, because the total holds them. Otherwise it is the card's Expenses that count in the month (`CountsOn`) plus its plans' installments still to come; for a card with stored bills, only the charges posted on or after the closing of the latest bill due before the month count, the earlier ones being inside a bank total. A card the bank sends no bills for uses every Expense, as before.
- **Other Bills**: every Bill of the month, paid or not, except one paid by a card Transaction (that money is in a card bill).
- **Installments off the card**: projected installments of plans on Sources that are not cards.
- **Planned spending**, per Spending Category: the plan is its Spending limit, or, with no limit, the average of what it spent in the 3 months before the current one (`plannedBaseline`: by `CountsOn`, without Expenses a Bill payment points to, and without the Expense off the cards nearest each registered Bill's expected amount (within a tenth) in each month, since the bank rarely names the Bill (`billPaymentRows`); a month counts when the User has any row in it, so a month the category spent nothing in is a 0 and months before the first data are not divided by; rounded half up to whole centavos, negative read as 0 after averaging; the same figure for every month of the horizon, anchored to the real current month, not `from`). The line is the plan minus what already counts for the category in the month (every Expense, card or not, plus installments still to come; in the current month the charges the shown card bills hold plus the month's Expenses off the cards), never below zero. Categories that plan 0 have no line.
- **Spent off the card**, current month only: that month's Expenses on Sources that are not cards, without those a Bill payment points to.
- **Saving** (`SavingCents`): the larger of the month's net `saving` rows (`MonthTotals.Saving`, so a Resgate lowers it, read as at least 0) and the Monthly contribution (0 when none). The two are never added: money already put aside this month counts toward the contribution.

`TotalCents` is the sum of the six, and the Leftover is `Monthly income − TotalCents`: negative when the month takes more, absent with no income. Because the Monthly contribution is inside the total, the Leftover is what remains after saving.

**`Extra` versus the Leftover.** The savings suggestion compares the Leftover with zero, not with the contribution: above zero, `Extra(in, leftover)` reruns the contribution split with `base + leftover` and returns all of the Leftover as the extra, with how many months sooner a target is reached; below zero, `OverLimit` lists the Spending Categories over their limit (see below).

**Committed and Spent since the 1st** (`GET /me/finance/transactions`). `Handler.Month` runs `loadOutlook` for one month: `committedCents` is its card bills plus `MonthTotals(...).Spend` of the counted rows on Sources that are not cards (Bill payments included: money out of the account is committed whether or not a Bill lists it). `spentSinceFirstCents` is `Store.SpentByPosted`: every Expense posted in the month, on any Source, by posted day rather than `CountsOn`. The gap between the two is earlier purchases on this month's card bills, or this month's card purchases falling on later bills.

## The contribution split

The contribution split says where this month's Monthly contribution goes: how much to the Emergency reserve, how much to each Goal, and the month each is expected to be reached. It is the rule `SplitContribution` in `finance/contribution.go`, pure like `CountsOn` and `MatchBills` (no database, HTTP or clock; `purity_test.go` lists the edge files and this is not one of them) and tested with table tests in the package (`contribution_test.go`). It is called "contribution split", never "allocation": Allocation is the Chores module ([ADR 0004](../adr/0004-ai-allocates-behind-a-deterministic-referee.md)). Only `GET /me/finance/savings` calls it, on every read; nothing it works out is stored.

**Inputs** (`ContributionIn`, all in centavos): the reserve target (nil when none is set) and the reserve's saved amount (the sum of the Investments that serve it); the Goals in the User's order, each with its target and its month (nil when it has no date); the Goals pot (the sum of the Investments that serve Goals); the base and the reserve's share in percent; and `Now`, the first day of the current São Paulo month, passed in so the rule never reads a clock.

**Outputs** (`ContributionOut`): this month's amount for the reserve and its expected month; for each Goal, in the input order, the amount already saved for it, this month's amount, the expected month and `Late`; and `Unassigned`, the money no Goal can take.

**The steps, in order:**

1. **Spread the pot.** The Goals pot fills the Goals with a date first, earliest month first (the User's order breaks ties), then the others in the User's order, each up to its target. What is left over goes to `Unassigned`.
2. **Simulate month by month,** from the current month, for at most 120 months (`maxContributionMonths`). Each month:
   - The reserve takes its share, `(base × percent + 50) / 100` in integer cents (rounding half up), but never more than it misses. With no target it misses nothing, so all of the base goes to the Goals; once it reaches its target it takes nothing more, and if its saved amount is below the target again it takes its share again. Whatever the reserve does not take joins the Goals' money, so the parts always add up to the base.
   - Each dated Goal, earliest first, takes `ceil(missing / months left including this one)`; a Goal whose month has passed counts as one month left and asks for all it misses. When the money runs out, the earliest are paid first.
   - What is left goes to the Goals in the User's order: the first not yet full takes what it misses, then the next.
   - The first month in which the reserve or a Goal reaches its target is its expected month. In the current month, any money no Goal takes is added to `Unassigned`.
3. **Expected months.** A target already met is the current month; one not reached within the 120 months is nil. With a base of zero no month is given at all. A Goal is `Late` when it has a date, the pot does not already fill it, and it is expected after its month or not within 120 months.

**Compared with the leftover.** `Savings` reads the current month's leftover from `loadOutlook`, the same function `GET /me/finance/commitments` uses, so Resumo's leftover card and the suggestion cannot disagree. With no Monthly income or no Monthly contribution there is no comparison. The leftover already subtracts the Monthly contribution ([the month outlook](#the-month-outlook-and-the-leftover)), so it is compared with zero. When it is above zero, `Extra(in, leftover)` runs the simulation a second time with the base plus the leftover, for every simulated month (the reserve's share is then taken of that sum), and returns the extra (the whole leftover) and how many months sooner the reserve is reached, or, when the reserve has no target or is already full, the first Goal the pot does not fill. `MonthsSooner` is nil when every Goal is full or either run does not reach the target within 120 months. When the leftover is below zero, `OverLimit(totals, limits)` returns each Spending Category whose spending this month (`MonthTotals` over the outlook's rows) passed its Spending limit, with the amount over, largest first. A leftover of zero gives neither.

**Known limits.** `contribution.go` has no `shortcut:` comments; these limits follow from the rule as built. Filling dated Goals first from the pot can leave the first Goal in the order with nothing, even when a dated Goal far away only needs a monthly slice. "Months sooner" assumes the leftover is saved every month, not only this one. With no history of contributions, the pot's spread is recomputed from today's values on every read, so it can move when the User reorders the Goals or adds a dated one.

## Voice commands

A Resident speaks one command; the browser turns it into text and the API turns that text into proposed actions. **The server only interprets, and the browser applies.** Each proposed action is the exact request an existing route already accepts (`POST /home/chores`, `PUT /home/chores/{id}`, `POST /home/tasks/{id}/accept|take|refuse|complete`), and the PWA sends it only after the Resident confirms. So voice grants no new permission, the screens' rules apply twice (once here, again at the route), a partial failure needs no new code, and nothing about the command is kept between the two steps. This is the one place the model sees Chore titles and the Resident's words ([ADR 0020](../adr/0020-voice-commands-send-chore-titles-and-the-residents-words-behind-a-confirmation.md)); the allocator, explainer and Categorizer still never do.

```mermaid
sequenceDiagram
    participant B as Browser (Web Speech API)
    participant P as PWA voice panel
    participant A as API: POST /home/voice/interpret
    participant D as Postgres
    participant L as Anthropic (tool calls)
    B->>P: transcript (the audio stays with the browser's speech service)
    P->>A: { transcript, locale }
    A->>D: this Home's Chores, today's Day Plan
    A->>D: reserve 1 of the Resident's 20 voice calls today
    A->>L: transcript + Chores + open Tasks + 6 tools (10s deadline)
    L-->>A: tool calls
    A->>A: strict decode, drop unknown or foreign ids, chores.Validate, cap at 5
    A->>D: one llm_call_events row, service voice
    A-->>P: { status, actions, remaining }
    P->>P: Resident removes, picks between matches, Confirm
    P->>A: existing routes, one after another
```

**The route and its guard.** `POST /home/voice/interpret` sits behind `requireResident`, wrapped in `voice.Handler.RequireConfigured`, which answers `503 {"error":"voice not configured"}` when `Deps.Voice` is nil (the same pattern as photos; local runs and CI have voice off). The body is decoded strictly with a 4 KB cap; a transcript that is empty after trimming, over 500 characters or holds a control character is `400 invalid_transcript`, a locale other than `pt-BR` or `en-US` is `400 invalid_locale`, and neither reaches the model or the counter.

**What the model sees.** The user message is JSON with the locale, the transcript, the Home's Chores (`id`, `title`, `category`, `effort`, `importance`, `people`, `interval_days`, `allowed_weekdays`) and today's open Tasks (`id`, `chore_id`, `people`, `relation`). No Energy, Restrictions, Preferences, Check-ins, Resident names or other Homes; two API tests walk the prompt's keys. Before the Day Plan exists no Tasks are sent, so a Task command then yields `nothing_understood`.

**The tools.** Six, all strict schemas whose Category, Importance and Demand enums come from `vocab`:

| Tool | Input | Becomes |
|---|---|---|
| `create_chore` | The `chores.Input` fields (`name`, `category`, `baseEffort`, `importance`, `intervalDays` null for one-off, optional `people`, `demands`, `allowedWeekdays`, `buildsUp`) | `POST /home/chores` with a body that passed `chores.Validate` (missing `people` is 1, missing lists are empty); otherwise dropped |
| `edit_chore` | `chore_ids` (every Chore the words may mean) and only the changed fields, null meaning unchanged; `one_off: true` makes it one-off, because a null `intervalDays` already means "unchanged" | The change laid over the stored Chore and validated as a whole, so a full `PUT /home/chores/{id}` body, with `changed` naming the fields that differ; an edit that changes nothing or breaks a rule is dropped |
| `commit_task`, `refuse_task`, `complete_task` | `task_ids` | `POST /home/tasks/{id}/<verb>`, the verb chosen by Go from the Task's relation (below), never by the model |
| `not_understood` | nothing | Nothing. It gives forced tool use a way to say the words are not a command, so noise does not become an action |

**Task relations.** Each open Task is sent with its relation to the speaker, read from `dayplan.Store.Today`: `proposed_to_you` and `committed_by_you` from the caller's own Tasks, `pool`, and `held_by_other`. A tool is allowed only where the route would accept it:

| Relation | `commit_task` | `refuse_task` | `complete_task` |
|---|---|---|---|
| `proposed_to_you` | `accept` | `refuse` | `complete` |
| `proposed_to_you`, two-person, the partner already committed | `accept` | dropped (Refuse would fail) | `complete` |
| `committed_by_you` | dropped | dropped | `complete` |
| `pool`, one person | `take` | dropped | `complete` |
| `pool`, two people, or `held_by_other` | dropped | dropped | dropped |

Restrictions, weekday limits and Drained are not checked here, since reading them is what voice must not do; the route's own `restricted` and `drained` errors cover them on Confirm.

**Turning calls into actions** (`interpretCalls`). The calls are untrusted. More than 5 calls other than `not_understood` is `too_many` with no actions. Each call is decoded with unknown fields refused, so a call that smuggles in extra text is dropped whole. Every id is checked against the set that was sent; unknown or foreign ids are removed and an action left with none is dropped. An action with two or more valid matches becomes `candidates`, each a fully resolved action of its own (two Chores can need different PUT bodies, and one Task can be `accept` and another `take`), and has no top-level request: the Resident picks. Identical actions are merged. No action left is `nothing_understood`. The response is `200 {status, actions: [{kind, request: {method, path, body}, taskId, choreId, choreName, changed, candidates}], remaining}`; `choreName` is the stored title, or for a create the validated name the model proposed, which is the one piece of model output the Resident sees. The model's free text never reaches the response.

**The daily limit and its record.** `voice.DailyLimit` is 20 calls per User per Home-local day, in `voice_calls` ([Data model](data-model.md)), apart from the Home's allocator and explanation cap in `llm_calls`. `reserveCall` is one insert-or-increment statement guarded by `WHERE calls < 20`, run on the pool rather than in a transaction, after the reads and right before the model call: concurrent requests cannot pass the limit, a failed read costs nothing, and a failed call still counts. Past the limit it answers `429 {"error":"voice_daily_limit"}`. The model call has a fixed 10 s deadline and 1024 output tokens; a timeout is `504`, an error or an answer that is not a tool-call list (or over 64 KB) `502`, both `{"error":"voice_unavailable"}`. Every outcome, `skipped_cap` included, writes one best-effort `llm_call_events` row with `service = 'voice'` (model, outcome, latency, tokens, estimated cost, calls sent and actions kept), which `GET /admin/ai` reports. The transcript is neither stored nor logged; an API test captures the logger to check it.

If storing fails after the copy, the new avatar is deleted and the answer is `500`. |
| `DELETE /me/photo` | Needs a token; `503` when photos are off. Clears the photo, then deletes the object (best effort); `204`, also when there was no photo. A removed photo may stay cached for up to a day. |
| `GET /push/vapid-public-key` | `{"key": "..."}`, the key browsers subscribe with. |
| `PUT /push/subscription` | Needs a token. Body is the browser's `PushSubscription.toJSON()` (`endpoint`, `keys.p256dh`, `keys.auth`, optional `userAgent`). Idempotent upsert on `endpoint`, owned by the caller (a device re-registered by another signed-in User moves to them); `204`. `400` for a non-https endpoint, missing or non-base64url keys or bad JSON; `413` over 8 KB. |
| `POST /push/test` | Needs a token. Body `{"endpoint","delaySeconds"?}`. Sends a small test notification to that one stored subscription only. `204`; `404` unknown, owned by another User or owned by nobody; `410` if the push service rejected it (the row is deleted); `502` on any other push error (the row is kept). |

Invalid Home settings answer `400 {"error":"invalid home","fields":{...}}` with every bad field and a stable code each: `timezone` is `required` or `unknown` (not an IANA zone; `Local` is refused because it means the server's zone), `allocationTime` is `required`, `invalid` (not strictly `HH:MM`) or `not_quarter_hour` (the Allocator job runs every 15 minutes, so only minutes 00, 15, 30, 45). Nothing is stored.
Every profile write answers `204` with no body, and every query uses the signed-in User's id, never one from the URL or body. Request bodies are capped at 4 KB and reject unknown fields (`httpx.DecodeBody` takes the cap and a strict flag; push keeps its 8 KB cap and lenient decoding).

The three `/push/*` routes answer `503 {"error":"push not configured"}` when no VAPID keys are set, so local development and CI need none. The two write routes need a signed-in User; `GET /push/vapid-public-key` stays public. Push configuration is checked first, then the token. Subscriptions carry `user_id`, and a test send reaches only a subscription the caller owns.

## The two test seams

A seam is the one place tests are allowed to push on the system.

```mermaid
flowchart LR
    T1["API tests (black box)"] -->|HTTP| S["server + real Postgres"]
    T1 -.-> F["fakes: Clock, Web Push, Cognito and the LLM client"]
    T1 -->|"RunAllocation"| P["dayplan.Planner, same database"]
    T2["Allocation tests (table-driven)"] -->|Plan, Check| A["allocation package"]
```

1. **The API.** `apitest.Start` runs the real server on a database cloned from a migrated template (`TEST_DATABASE_URL`), with a fake clock; `apitest.WithPush(key)` adds the recording fake Web Push sender, exposed as `App.Push`; `apitest.WithPhotos()` adds the in-memory `photos.Fake` (exposed as `App.Photos`) and the base URL `apitest.PhotosBaseURL`. `Start` always wires an `auth.Fake`; `App.SignInAs(email)` returns a client whose requests carry that fake's bearer token (the same email is the same User), and `apitest.WithoutAuth()` leaves the Verifier nil for the 503 case. `Client.JoinHome(t, homeID)` inserts a `residents` row for a signed-in User so tests can have several Residents without the Invite flow. `App.RunAllocation(t)` runs the Allocation job once at the fake clock's time over the same database, exactly as the scheduled tick does, and `App.UseAllocator(a)` swaps in a stub allocator (for example one the referee must reject). Tests assert on HTTP responses, never on internals, except the run record, which the job writes and only the database shows.
2. **Allocation.** Pure-function tests on `Plan` and `Check`.

There is no automated UI test; the web app is type-checked and built in CI.
